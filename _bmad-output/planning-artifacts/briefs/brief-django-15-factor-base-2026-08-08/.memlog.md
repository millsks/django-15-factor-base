- (event) SECURITY-RELEVANT FINDINGS - three cookiecutter-django credential paths survive and contradict the OIDC-only posture: (1) DJANGO_ADMIN_FORCE_ALLAUTH defaults to False so /admin/ serves Django's own password form via ModelBackend, bypassing the IdP; (2) DRF DEFAULT_AUTHENTICATION_CLASSES includes TokenAuthentication with rest_framework.authtoken installed - static tokens, no IdP; (3) ACCOUNT_LOGIN_METHODS={username} enables local username/password login in allauth.
- (decision) Django admin and django-cors-headers promoted to immovable core. Toggle list now: async tasks (Celery), Redis cache, server-rendered UI, object storage.
- (decision) All three credential paths to be rewired to IdP-only. NO local user authentication of any kind. Authorization via an IdP group claim mapped onto the user profile.
- (event) OIDC feasibility check: allauth ships socialaccount/providers/openid_connect, so the INTERACTIVE browser flow (admin + web UI) needs no new dependency - and users/admin.py already wires allauth's secure_admin_login behind DJANGO_ADMIN_FORCE_ALLAUTH, so forcing admin through the IdP is a one-line default flip. No JWT/JOSE library is installed, so the PROGRAMMATIC DRF flow does need a new dependency.
- (decision) DRF TokenAuthentication CANNOT be adapted to OIDC - it is hardwired to rest_framework.authtoken's local Token model with no issuer, signature, expiry or claims. It must be replaced by a Bearer/JWT authentication class validating IdP-issued access tokens against the IdP JWKS, and rest_framework.authtoken dropped from INSTALLED_APPS.
- (assumption) ACCEPTED RISK to confirm: with zero local authentication there is no break-glass account. If the IdP is unavailable, nobody can reach Django admin. Also: IdP group claims must be re-synced on EVERY login, not just at signup, or IdP-side revocation never propagates.
