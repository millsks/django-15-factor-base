- (decision) The mapper is TWO operations at different frequencies. RESOLVE: given claims, find the user by the identity key - runs on every authentication including every Bearer request, single indexed read-only lookup. SYNC: diff asserted groups against stored, add/remove, set staff+superuser, emit the structured log line - runs once per credential epoch (every interactive login; once per Bearer token, first sighting of its jti). Prevents: conflating them, which yields either auth_user_groups write amplification per API call or stale authorization. There is no third outcome.
- (decision) Identity key storage: a new field User.idp_subject - unique, indexed, nullable (local-only accounts exist where refusals do not apply). It is the SINGLE store; the allauth adapter resolves through the mapper too, leaving SocialAccount as bookkeeping rather than authority. Prevents the interactive flow resolving via SocialAccount.uid while the Bearer flow resolves via idp_subject, which is exactly the divergence FR-8 forbids (same identity, both orders, same user). Field is named for its role because FR-10 keeps the claim NAME configurable. Current state: users.User is AbstractUser, username-keyed, get_absolute_url routes by username.
- (decision) USER: a token that arrives without the configured group claim is rejected with 401, not authenticated with zero groups. A trusted issuer emitting a token that lacks what our claims contract requires is a misconfiguration and should not present as a permissions bug.
- (decision) USER: a claim asserting a group with no matching Django Group is IGNORED AND LOGGED, never created. Prevents an IdP typo creating permanent rows in every component in the estate, and stops IdP group taxonomy silently becoming Django taxonomy.
- (decision) USER: designated groups confer both is_staff and is_superuser, per FR-11. No divergence from the PRD.
- (decision) Three roles kept separate: CREDENTIAL (enterprise username + whatever the IdP enforces - lives at the IdP; a deployed component authenticates nobody), IDENTITY KEY (User.idp_subject - what the mapper resolves by), ATTRIBUTE (username/email/name - populated from claims, displayed, used in URLs, never resolved by). USERNAME_FIELD stays 'username' so Django's own machinery keeps working.
- (decision) USER: on a username collision during sync (AbstractUser.username is unique=True; two distinct idp_subjects presenting the same preferred_username - rehire, name change into a taken value, merged directory) the mapper REFUSES THE COLLISION AND LOGS. The second identity keeps its existing username and authenticates normally. Prevents an IntegrityError mid-authentication locking someone out, and prevents a silent uniquifying rename. Note: get_absolute_url routes by username, so a synced username changes a user's detail URL.

- (decision) Dependency direction across the three code territories, fixed because all of them look legal to a compiler: a tenant app under src/django_apps MAY import django_service; django_service MAY NOT import any tenant app, ever (a base that depends on what is built on it is no longer reusable and the twelve-combination harness stops meaning anything); config may import django_service and reaches tenant apps only through the settings composition step, never by direct import; a feature's code MAY NOT import another feature's, or the carrier's surfaces stop being independently removable.
- (decision) USER: django_service exposes an API VERSION CONSTANT, bumped by hand when the public surface changes.
