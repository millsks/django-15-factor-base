02 — The shape

Two products share one tree

The accelerator is manifest-driven projection: one hand-authored catalogue, many derived artifacts. Twelve materialized source trees, the disposition rule, the orphan checks and the eventual FreeMarker copy are all projections of the same file.

The component is layered Django with a composition root, plus a plugin space. Its base package is a stable public API that reusable apps import by a constant name.

03 — Load-bearing decisions

The eight that carry the rest

Thirty-two decisions are recorded in the spine. These eight are the ones whose absence would let two competent epics build incompatible things — expand any one for the alternatives it beat.

AD-3Materialization is subtractive, and dependencies are native pixi features

The materializer copies the reference application and removes what the carrier says a combination did not select. The four features are pixi features with an [environments] matrix, so one lock file yields twelve pre-locked environments — all sharing one solve-group.

Why, and what lost

Three alternatives were weighed: in-source markers alone, an external manifest, and full composition from per-feature fragments. Composition lost because it would make the reference application itself a materialized artifact, which changes what this repository is and makes "output for the all-features combination equals the reference application" trivially true and therefore worthless as a check.

The pixi feature matrix was the decisive addition. Without it, twelve combinations mean twelve dependency solves, or — worse — twelve gates running in one fat environment where a combination that accidentally imports celery still passes. With it, combination seven's environment genuinely lacks celery, and the hole closes structurally rather than by a check someone has to remember to write.

The solve-group clause was added after review: django-celery-beat caps django <6.1 and Django 6.1 is on the channel, so without it the four Celery combinations would resolve a different Django from the other eight, and "all twelve pass" would be measuring two different things.

AD-5django_service is public API, not a package name

The name is a constant, never parameterized. Moving a module inside the guaranteed surface, changing AUTH_USER_MODEL, or renaming a guaranteed setting is a breaking change, tracked by an integer __api_version__.

Why, and what lost

The PRD lists src/django_service/ under paths the materializer parameterizes. That is wrong, and the reason matters: reusable apps import from it. An app doing from django_service.users.models import User only works if that name is identical in every deployment. Parameterize the package and every reusable app breaks in every component that renamed it differently.

So the constant is not a convenience — it is what makes apps portable across components at all. The consequence is that a routine tidy-up inside the base becomes an estate-wide break, which is why the version constant exists and why AD-29 forbids feature dispositions inside the package.

This also deleted a whole planned work item: the readiness review ranked the package rename medium-high and warned it would conflict with every in-flight branch at once.

AD-10The mapper is two operations at different frequencies

Resolve — find the user by identity key — runs on every authentication, including every Bearer request. Sync — diff groups, write memberships, set staff and superuser — runs once per credential epoch, in one transaction.

Why, and what lost

The requirement says the mapper runs "on every authentication." For a browser login that is once. For DRF that is every single request — so read literally it mandates a group diff and up to two writes per API call, forever, for one identity.

The obvious fix — cache the whole mapping per token — quietly reintroduces the revocation latency the requirement exists to eliminate. Splitting the operation is the only answer that gives neither outcome: resolution stays per-request because DRF needs request.user, and the writes happen once.

Review found two gaps in the first version. The epoch record cannot live in django.core.cache, because eight of twelve combinations have no Redis and the in-process backend degrades "first sighting" to first-sighting-per-worker-per-restart. And a token with no jti had no rule at all — one builder would sync every request, another would never sync again, delivering both outcomes this decision claims to prevent. It is now a 401.

AD-11One identity key; credential, key and attribute stay separate

The IdP holds the credential. User.idp_subject is the identity key and the sole store. username, email and name are attributes — displayed, used in URLs, never resolved by.

Why, and what lost

Resolving users by email is the instinct and it fails two ways. Someone changes their address at the IdP and the next sign-in creates a second account, orphaning their groups and history. Or two identities present the same email claim — reused after a leaver, or simply unverified — and the second inherits the first's authorization. That is account takeover, and it is silent.

The subtle half is that allauth already stores a subject in SocialAccount.uid. If the browser flow resolved there and the Bearer flow resolved on idp_subject, the same person seen first through the API and later through the browser would become two users — the exact divergence the single-mapper rule exists to stop. So idp_subject is the only store and allauth becomes bookkeeping.

AD-13Locality and process type are declared per pixi task

Local tasks set COMPONENT_RUNTIME=local in their own task env. web, worker and beat set nothing and inherit deployed, and each sets COMPONENT_PROCESS. No COMPONENT_* variable may appear in [activation.env].

Why, and what lost

The requirement assumed the local declaration would be inert in production "because a container runs its server process directly." On this platform that is false: the golden base image has pixi and deployment runs pixi run web. So anything in [activation.env] — where COVERAGE_CORE already lives — reaches production and declares it local, and you would then need deployment to remember to override it. That inverts the fail-closed property that is the whole point.

Per-task env is precise instead of structural, and it pays off twice. It kills the trap where a fail-closed environment rule refuses the entire test suite on the first run after landing. And it lets the same declaration carry the process type, which means the process model, the locality rule and the per-process scoping of the refusals are one declaration rather than three that can disagree.

AD-26The refusal contract has one location, one owner, and a fixed order

One module at src/config/startup/, holding both stages and the allowlist. Stage 1 is the last statement of every settings module. Stage 2 is owned by one named core AppConfig. Predicates resolve objects, never strings.

Why, and what lost

This is the product's highest-consequence surface — the separation between a local component and a deployed one rests entirely on it — and the first draft of this spine did not say where it lived. Two developers could both satisfy the requirement and end up with the contract in two different modules, one of them coupled to an app the UI feature edits.

Ordering turned out to be load-bearing for a reason nobody had noticed: the reusable-app composition step appends to the end of base.py, and stage 1 runs at import. Put stage 1 anywhere but last and a contributed database with its automatic local substitution is never seen by the sqlite refusal — a deployed component serving a contributed database out of a sqlite file.

"Predicates resolve objects" closes the sharpest hole review found. Fixing the local sign-in path's shape is not enough: a route named local_persona_login mounted under /accounts/ satisfies every stated rule, escapes a name-matching refusal, and passes an allowlist that already permits /accounts/ for allauth — shipping a live persona sign-in into production.

AD-27Authorization data has an owner

Group and Permission rows are provisioned by a data migration inside django_service, seeded from the claims contract. The local persona task calls that same mechanism. A designated group missing at startup is a refusal.

Why, and what lost

Without this, every deployed component grants nobody any authorization and nobody can reach the admin — and all twelve local smoke checks pass anyway.

The chain: the persona epic seeds groups locally, so the harness is green. Deployed, the seeding task is refused, the mapper may not create groups, createsuperuser is retired, and the component cannot migrate itself. The first real sign-in asserts the staff group, no group matches, the claim is ignored and logged, is_staff is never set, the admin is unreachable — and the only place a human could create the group is the admin.

Requiring the persona task to call the provisioning mechanism rather than reimplement it is the part that makes the harness able to see the failure at all.

AD-30The core has an unprunable assertion suite

The smoke check asserts a rendered admin index, a real Bearer request and a rendered 404 — not just boot and sign-in. A core-disposed core assertion suite runs inside every combination's gate and no feature can prune it.

Why, and what lost

The coverage signal that catches incomplete feature removal is asymmetric by construction. It catches a template left behind, because it reports zero. It is structurally blind to a template wrongly removed, because the removed thing's tests left with it, coverage measures only what remains, and the floor is still met.

Concretely: take templates/ wholesale as UI-owned and six combinations lose base.html, which the 403, 404 and 500 pages extend. Every check in the harness passes. Nothing renders an error page.

So one success criterion — "excluded features leave nothing behind" — was well defended, and its twin — "the immovable core functions in every combination" — was defended by nothing at all.

The remaining twenty-four decisions cover dependency direction, the tenant-space contract, parameterization, health and drain, provenance, the gate, and the coverage floor. All of them are in ARCHITECTURE-SPINE.md alongside this page.

04 — Traded knowingly

What this costs

The product's own requirements document is deliberately unflattering about itself. A uniformly confident architecture document would misrepresent it. These are accepted, not mitigated.

R-1 · unproven fitness

django-storages 1.14.6 is on the approved channel — but it was released in April 2025 and declares no Django 6.0 or Python 3.14 support; that support exists only on unreleased upstream master. Object storage is in six of twelve combinations, does not exist yet, and most components will select it, so deferring it is not available. Escalation is ordered: spike compatibility first, then push the channel feedstock with a time-boxed exception, and only as a last resort own an S3 backend. A permanent supply-chain exception is not on the list.

R-2 · revocation latency

Syncing once per token means a group revoked at the identity provider is honoured until that token expires. This is unavoidable for bearer credentials — the claims are in the token — but it narrows the requirement, and it is not the same question as the open one about session lifetime.

R-3 · a fail-open hole

A serving process started outside pixi run web does not fire the unapplied-migrations refusal. Process type fails open deliberately; failing it closed would make manage.py migrate — the one action that clears the condition — refuse to run.

R-4 · two component shapes

"Use this template" on GitHub produces a fork of the base, not a generated component. It copies the default branch, so the reduced-verification-on-PR argument does not hold for it; it carries the machinery Dockerfile, so it can opt out of the platform image pipeline; and it can adopt reusable apps where a materialized component cannot. A component that must carry the platform's guarantees is materialized, not templated.

R-5 · local runs prove less than they look like

Inherited unchanged from the requirements: sqlite accepts schemas PostgreSQL rejects, eager execution never exercises delivery or retries, and synthetic claims never exercise key retrieval or rotation. The gate covers all three, so this is a slower feedback loop rather than an unverified product — but a component running locally is not evidence it will run deployed.

05 — Diverges from the PRD

Five places the documents disagree

Each needs the requirements amended or this spine corrected. They must not be left to disagree silently.

D-1

The PRD parameterizes src/django_service/. It is a constant — see AD-5. This also dissolves a work item the readiness review ranked medium-high.

D-2

The PRD requires the materializer's declarations be authored once and shared with the eventual template, cross-checkable during the transition. The FreeMarker copy is one-way and out of tree, so it is really "derived once, then drifts."

D-3

"On every authentication" is narrowed to once per credential epoch for the API flow. Deliberate; the consequence is R-2.

D-4

The PRD says the browser flow costs no new dependency. It costs requests — imported directly by the OIDC provider, absent from the channel recipe's declared dependencies, and reaching the environment only transitively through the telemetry exporter.

D-5

The PRD does not know about reusable apps, src/django_apps/, or the GitHub-template consumer. All three govern real invariants here.

07 — Rules that bite

If you are new here

Six things that look like ordinary Django and are not. Every one of them is invisible in compliant code, which is exactly why they are written down.

The package name is not yours to change

django_service is a constant everywhere, in every deployment. Reusable apps import from it by that name. Renaming it, or moving a module inside its guaranteed surface, breaks every app anyone has written on top.

Your app goes in src/django_apps/, and that directory has no __init__.py

It is a path root, not a package. An app at src/django_apps/billing/ is imported and installed as billing — unqualified. That is what lets it graduate to a channel package later without its import path changing.

Your app may add configuration, never change it

Contribute a new key and the composition step merges it. Touch a key that already exists and the component refuses to start. Additions to ordered lists append in adoption order. The contributable surface is closed and enumerated — global defaults like MIDDLEWARE and DRF's permission classes are refused, whether or not the base already sets them.

Nothing sets sys.path, and nothing puts COMPONENT_* in [activation.env]

Import roots are declared in the build configuration alone. And because the deployed image runs pixi, anything in activation env reaches production — which is how you would accidentally declare production to be a local development machine.

A deployed component authenticates nobody

The identity provider does. There is no local login form, no static token, no break-glass account. Nine startup conditions refuse a component that has any of them, and an allowlist test fails the build if you add a credential path without deciding to.

Coverage includes templates, and that is not a formality

It is the only signal that catches a feature extraction that left something behind. Do not add to the coverage omit list, do not add pragmas, and do not lower the floor — those are named as forbidden precisely because each of them makes the number go green while destroying what it measures.
