- (capability) CAP-2 IdP-only authentication with one shared mapper: interactive and programmatic flows both resolve authorization through a single mapper keyed on one stable identity claim. Success: SC-6 - a real IdP identity authenticates through both flows and resolves to the same user in either order, with memberships added, removed, and staff/superuser set from designated groups. - (capability) CAP-3 The refusal contract: nine conditions evaluated at two defined points, independently of which settings module loaded. Success: SC-5 - each of the nine has a test that configures the forbidden state and asserts ImproperlyConfigured, and the authentication surface matches its allowlist exactly. (PRD 4.3, FR-12..FR-17)
- (capability) CAP-4 Local development with nothing installed: five designed substitutions plus seeded personas and a locally signed development token, with observability deliberately unsubstituted. - (capability) CAP-6 Materializer and two-level verification: any valid combination is produced deterministically from the reference application and put through both verification levels before the FreeMarker transition. Success: SC-1 - all twelve materialize and pass the full gate against PostgreSQL, with any reduction of the set reported explicitly. (PRD 4.6, FR-30..FR-37)
- (capability) CAP-7 Deployment interface: the component declares its process model, health semantics, drain ordering and release-stage migration step to a deployment repository it does not own. - (capability) CAP-8 Observability: correlated structured logs and distributed traces that no feature selection can remove and no local substitution replaces. - (capability) CAP-9 Supply chain policy: every dependency resolves from the approved channel, and a feature is not committed to until its dependencies are proven both present and fit against the pinned runtime. Success: a test asserts no third-party package resolves from the package index, with the editable self-install the only permitted entry. (PRD 4.9, FR-49..FR-50)
- (capability) CAP-10 Extension model: a component extends through a declared tenant space with reusable apps that contribute configuration additively on a closed surface and keep their import path when they graduate to the channel. Success: an app adopted outside the base's declared compatibility range fails the component's gate, and writing to configuration the component already defines raises ImproperlyConfigured at startup. (PRD 4.10, FR-51..FR-56)
- (constraint) The IdP is the only credential authority in a deployed component; every local credential path exists only where the refusals do not apply, and a refusal never degrades to a warning (CG-3).
- (constraint) Authorization is decided in exactly one place - the mapper at src/config/authorization/ - and resolution is keyed on one stable identity claim, never email or username.
- (constraint) Deployment is the default and local development is the exception that must declare itself: COMPONENT_RUNTIME absent or unrecognized means deployed, and the declaration is carried by the local pixi task env, never by a file in the source tree or [activation.env].
- (constraint) Every dependency resolves from conda-forge; [pypi-dependencies] carries the editable self-install and nothing else. Zero exceptions as of 2026-08-14. A feature is not committed to until its dependencies are proven present AND fit against the pinned Django 6.0 and Python 3.14.
- (constraint) src/django_service/ is a constant, never parameterized, and no feature:* disposition may apply to any path inside it - reusable apps import from it by that name in every deployment.
- (constraint) The coverage floor is ninety percent including templates, globally, with COVERAGE_CORE=ctrace in force in every combination and the omit/exclude list a closed carrier-declared surface. Never a lower floor, a pragma, or a narrowed measurement (CG-1).
- (constraint) Any bound on the verification set is reported explicitly with the combinations not covered; a silently truncated set reads as full coverage (CG-2, FR-35).
- (constraint) A substitution is warranted only where the deployed dependency cannot be present on a developer's machine without becoming the service dependency the local contract exists to remove; the count is not the constraint, the principle is (CG-4).
- (constraint) Nothing on the local start path reaches the network at boot: OIDC discovery and JWKS retrieval are lazy, on first use only.
- (constraint) No network surface exists beneath Django's URL routing - a protocol handled below the resolver is invisible to the FR-17 allowlist and is never an inherited handler.
- (constraint) Configuration is exclusively environmental; no configuration file is baked into the image, and a materialized component ships no Dockerfile.
- (constraint) Dev/prod parity is deliberately traded (factor 10): backing services differ between local and deployed. The trade is bounded by the gate running against PostgreSQL, shared rather than mocked authorization code paths, and observability that is not substituted at all.
- (constraint) All twelve pixi environments share one solve-group; without it django-celery-beat's Django cap makes the four Celery combinations resolve a different Django and SC-1 stops meaning what it says.
- (constraint) Concrete non-functional numbers - probe timings, startup budget, termination grace, resource limits, JWKS cache TTL - are outside this contract and are pinned against the real platform.
